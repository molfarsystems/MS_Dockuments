## Правила міграцій (патерн creator/ArchivistDB)
1. `_connect()` → `PRAGMA user_version`; 0 → створити схему і виставити версію;
   `< VERSION` → `_migrate(from, to)` покроково (`if from_version < N:`).
2. Тільки незруйнівні кроки: ADD COLUMN з DEFAULT; backfill — через Python,
   якщо потрібен casefold/логіка (LOWER() у SQLite — ASCII-only!).
3. UNIQUE-пастки враховувати: мʼяке видалення звільняє імʼя (`~del#id`),
   backstop `_free_deleted_name` перед INSERT/UPDATE — [[13_Уроки_і_патерни]] §4.
4. knowledge.db — самодостатня (власні PRAGMA, без імпорту schemas), можна
   зносити: перебудовується індексацією.

## Історія міграцій knowledge.db
- v1→v2: веб-джерела (source_type/url/title/query у documents).
- v2→v3: `chunks.text_norm` (casefold-копія) + Python-backfill — пошук
  кирилиці регістронезалежно в SQL. `replace_chunks` пише text_norm завжди.

## Семантика ключових таблиць
- `chat_messages.chat_index`: 1..4 учасники, 5 Оркестратор, 6 Секретар;
  спільний чат InfoTab пишеться окремими вставками.
- `haiduk_documents`: ЛИШЕ посилання (filename, text_bytes=байти витягнутого
  тексту); текст перечитується з файла. `haiduk_doc_add` — атомарний
  DELETE+INSERT за іменем (один рядок на файл гарантовано).
- `project_documents.text_bytes`: у нових записах — байти ТЕКСТУ (уніфіковано
  2026-07); legacy-рядки могли містити розмір файла — допустимо, без міграції.
- `project_slot_documents` — посилання слота на файл пулу; чистяться при
  видаленні файлу (`proj_doc_delete`) і видаленні проекту.
