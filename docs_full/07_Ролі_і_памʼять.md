# 07. Ролі і памʼять

> Актуально: 2026-07.

## Ролі (roles.db v2 + modules/roles_*)
- Два види: `roles_participant` і `roles_orchestrator` (whitelist
  ROLES_TABLE_MAP). Роль = name, slug, prompt, skill, builtin-прапорець.
- Сид: `roles_seed.py` (найбільший статичний файл) — набір «спеціалістів»
  для учасників і оркестраторів; сідяться в creator.initialize.
- Дзеркало на диску: `Roles/{slug}_{id}_{hash6}/prompt.md, skill.md` —
  БД первинна, файли перегенеровуються (зручно читати/редагувати ззовні).
- Редактор: roles_modal (каталог) + md_editor_modal (лічильники лімітів
  довжини промпта/скіла).
- Мʼяке видалення ролей: name-mangling `~del#id` при UNIQUE — той самий
  патерн, що в проектах.

## Застосування ролей
- Учасник/Оркестратор: role_system = prompt + skill накладається поверх
  місця (schemas) при зборі system у project_chat_screen.
- Гайдук: роль поверх HAIDUK_PLACE_BODY; вибір зберігається в config.ini
  (відновлюється між сесіями); «скинути роль» — у нижньому модалі «+».

## Памʼять Оркестратора (memory.db v1 + memory_manager)
- Запис: після синтезу раунду `_store_orchestrator_memory` кладе суть
  (category, importance, tags); є batch-вставка для LLM-extraction
  (серіалізована write_lock-ом).
- Читання перед синтезом: pinned-записи + `search(query)` — вибірка
  рядків проекту в SQL (порядок importance+pinned*10, last_used_at),
  збіг підрядка — Python casefold (кирилиця!), ліміт 5.
- `mark_used` інкрементить use_count/last_used_at для використаних.
- Валідація: категорії whitelist, importance 1..10, кламп довжин
  (2000/500/300).
- UI: перегляд/пін/редагування записів з екрана наради.

## Звʼязки
Памʼять — ТІЛЬКИ для Оркестратора (слот 5). Секретар знання бере з
knowledge.db ([[08_Двигун_знань]]); учасники 1–4 памʼяті не мають —
їхній контекст = історія чату + документи слота.
