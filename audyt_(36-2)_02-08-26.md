## 3. 🔴 СЕРЙОЗНІ ЗНАХІДКИ

### 3.1. Розбіжність package id (buildozer.spec ↔ документація)
- **Файл:** `buildozer.spec`
- **Факт:** `package.domain = com.nova_hata`, `package.name = molfar` → фактичний applicationId = **`com.nova_hata.molfar`**.
- **Задокументовано в проекті:** `org.molfar.system.molfarsystem`.
- **Ризик:** після першої публікації в Google Play id змінити неможливо. Якщо `com.nova_hata.molfar` — свідомий вибір, треба виправити документацію; якщо ні — виправити spec ДО релізу.
- **Дія:** узгодити одне з двох джерел правди.

### 3.2. downloads.py — «Зберегти в Download» зламане на Android 7–9
- **Файл:** `downloads.py` (`_save_legacy_public`) + `buildozer.spec`
- **Факт:** гілка для API 24–28 пише напряму в публічний Downloads і потребує `WRITE_EXTERNAL_STORAGE` (docstring модуля сам це каже). У spec дозволи лише `INTERNET,ACCESS_NETWORK_STATE,VIBRATE`.
- **Наслідок:** при `minapi = 24` пристрої Android 7–9 підтримуються, але збереження **завжди тихо падає** з `legacy_err` (без краху, але функція мертва).
- **Варіанти виправлення (на вибір):**
  1. Додати в spec `WRITE_EXTERNAL_STORAGE` (бажано з `android:maxSdkVersion="28"` через android.manifest, щоб Play не чіплявся);
  2. Підняти `android.minapi = 29` (відсікає ~старі пристрої, спрощує код — гілку legacy можна видалити);
  3. Лишити як є, але чесно показувати користувачу на API<29, що функція недоступна.

## 4. 🟡 СЕРЕДНІ

### 4.1. `_sync_registry` не досіює нові моделі існуючим інсталяціям
- **Файл:** `ai_config_manager.py` (`_sync_registry`)
- **Факт:** `default_models` вставляються лише в гілці `row is None` (свіже створення провайдера). Гілка existing оновлює тільки display_name/kind/base_url/sort_order.
- **Наслідок:** після оновлення застосунку з розширеним каталогом у `providers_registry.py` старі користувачі нових моделей не бачать — лише ручне додавання через models_modal.
- **Виправлення:** у гілці existing додати цикл `INSERT OR IGNORE INTO models ...` по `default_models` (UNIQUE вже захищає від дублів).

### 4.2. pop_ai: «хвіст без відповіді» в БД при помилці API
- **Файл:** `pop_ai.py` (`send_message` / `_on_api_error`)
- **Факт:** фікс Г5 не персистить питання, коли нема моделі/ключа. Але в основному флоу питання пишеться в chat_history.db **до** запиту; якщо API повертає помилку/таймаут — user-повідомлення лишається в БД без assistant-відповіді (та сама проблема, що Г5 виправляв, тільки в іншій гілці).
- **Наслідок:** після рестарту в історії Гайдука висять питання без відповідей.
- **Виправлення (варіанти):** (а) персистити user-повідомлення лише в `_on_api_done` разом із відповіддю; (б) в `_on_api_error` видаляти останній user-запис; (в) персистити error-запис як пару (роль 'error' в схемі вже передбачена).

### 4.3. API-ключі — два ризики безпеки
- **Файли:** `ai_config_manager.py`, `google_adapter.py`
- **(а)** Ключі зберігаються plaintext у `ai_config.db`, який лежить у **видимій користувачу** зовнішній теці (`Android/data/<pkg>/files/...`). Бекап/шаринг теки = злиття ключів. Мінімум — задокументувати ризик; краще — тримати ai_config.db у приватному `user_data_dir` (Android 11+ інші застосунки й так не читають Android/data, але видимість користувачу лишається фактором).
- **(б)** `google_adapter` передає ключ у **query string** (`?key=...`) — такі URL логуються проксі/аналітикою. Виправлення: заголовок `x-goog-api-key` замість query-параметра.

### 4.4. print() замість єдиного логера (порушення власної конвенції П10)
- **Файли:** `archivist_engine.py` (6 місць: рядки ~231, 394, 434, 558, 651, 672), `archivist_db.py` (~15+ місць по всьому файлу).
- **Факт:** увесь проект переведений на `app.logger.get_logger`, ці два модулі — ні.
- **Наслідок:** повідомлення двигуна знань не фільтруються logcat-тегом 'molfar', нема рівнів.
- **Виправлення:** механічна заміна `print(f"[ArchivistDB] ...")` → `log.error/info(...)`.

### 4.5. main.yml — PR із форків завжди «червоні»
- **Файл:** `main.yml`
- **Факт:** секрети недоступні у fork-PR → крок `Restore upload keystore` робить `exit 1`, весь workflow фейлиться, хоча debug-APK зібраний і вивантажений.
- **Виправлення:** гейтити release-частину (keystore → aab) умовою `if: github.event_name != 'pull_request'` або перевіркою наявності секрету без exit 1.

## 5. 🟢 ДРІБНІ

### 5.1. Мертвий fallback-шлях у _exports_base
- **Файл:** `chat_tabs.py:135` — кандидат `/storage/emulated/0/Molfar_System/Exports`. На Android 11+ write-test завжди падає (Scoped Storage); безпечно, але шумить у логах і вводить в оману. Те саме — `EXTERNAL_BASE` у `creator.py:43` (там хоч чесно позначено «desktop-fallback, на Android НЕ використовується»).
- **Виправлення:** прибрати кандидата або обгородити `platform != "android"`.

### 5.2. downloads: дрібниці desktop/MIME

- **Файли:** усі менеджери БД (chat_db_manager, ai_config_manager, db_manager, memory_manager, participants_manager, roles_manager, archivist_db).
- **Факт:** типовий патерн `conn = ...; conn.execute(...); conn.close()` усередині try — при винятку конекшн не закривається явно (GC врятує; з WAL + busy_timeout некритично).
- **Виправлення (за бажанням):** `try/finally` або контекст-менеджер `contextlib.closing`.
